# V0.8 — Authoritative economy staging handoff
Status: **SQL code committed; not deployed, no live multiplayer or cloud sync.**

## Architecture
- Supabase Auth from V0.7 identifies the user. Each player has one `player_farms` row provisioned by a trusted administrator.
- `farm_state`: authoritative coins (100 initial), harvest count, monotonically increasing revision.
- `farm_plots`: 64 plots, crop id and PostgreSQL server timestamp. Cost, growth duration and reward are hard-coded on the server to match `lib/farm-demo.ts`.
- `farm_commands`: owner-scoped UUID idempotency journal. A duplicate request returns its original result; same UUID with altered payload is rejected.
- `farm_apply_command`: single atomic SQL transaction, per-user advisory transaction lock, ownership derived exclusively from `auth.uid()`, row locks, server timestamp, balance check, and revision increment. Direct client writes are denied.
- No localStorage import/sync. Offline V1 save and V2 progression remain unchanged; no merge or automatic upload.
- This is **not** yet a full online gameplay UI: it is a reviewed server-side foundation only.

## Setup (NEW staging project ONLY)
1. Complete V0.7 Auth and RLS setup, including two test accounts and provision their own player_farms via a trusted admin path.
2. Apply `db/migrations/0003_v08_authoritative_commands.sql` only after V0.7 migration; never apply to live DB without explicit approval.
3. As account A, call authenticated Supabase RPC `farm_apply_command` with a random UUID, action `plant`, plot 0, crop 0. Expect coins 99 and revision 1.
4. Retry exact same UUID/payload: expect unchanged revision and coins. Reuse UUID with another payload: expect error.
5. Try harvesting immediately: must fail. Advance test database clock in an isolated controlled test or wait 120 seconds, then harvest using a fresh UUID: expect coins 102, harvested 1, revision 2.
6. Test two accounts: A cannot read B state/plots or modify B. No direct client INSERT/UPDATE/DELETE succeeds. Test unauthenticated RPC denied.
7. Send concurrent plant requests on the same plot with distinct UUIDs: exactly one succeeds. Simulate network timeout/retry; verify exactly-once effect.
8. Test insufficient coins, invalid crop/plot, null inputs, premature harvest, stale session, database rollback, and missing farm.
9. Validate migration against Supabase Postgres staging, review SECURITY DEFINER permissions and advisory lock behavior. Run CI, then inspect Pages.
10. **Do not** enable online game commands or cloud migration until all checks pass, monitoring/backups exist, and explicit activation is approved.

## Rollback
Disable the client feature flag first. Keep the offline game available. Restore staging from verified backup if schema rollback is needed. Do not drop data-bearing tables automatically.
